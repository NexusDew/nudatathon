# Контроль кассовой дисциплины по видео — документация к сдаче

Сервис принимает видео рабочего места кассира и возвращает список возможных нарушений:
таймкод, тип, кадр-доказательство и ссылку на норматив РК. Все модели работают локально.

- Веб-интерфейс: https://fiddling-uncheck-decency.ngrok-free.dev/ (в браузере ngrok сначала покажет
  страницу-предупреждение — нажать «Visit Site»; на API это не влияет)
- API: `POST /api/v1/analyze` (multipart, поле `file`) → `job_id`; `GET /api/v1/jobs/{job_id}` → статус
  `processing` / `done` / `failed` и результат по схеме ТЗ. Заголовок `X-API-Key` обязателен, без него — 401.

## 1. Запуск

```bash
python -m venv .venv
.venv\Scripts\activate            # Linux: source .venv/bin/activate
pip install torch torchvision --index-url https://download.pytorch.org/whl/cu128
pip install -r requirements.txt
python scripts/download_weights.py --dir D:/nudatathon_weights --only dfine,qwen8b,llamacpp
copy .env.example .env            # задать API_KEY
```

Запуск — два окна PowerShell:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\start.ps1          # VLM-сервер + API/UI на 127.0.0.1:8000
powershell -ExecutionPolicy Bypass -File scripts\tunnel_ngrok.ps1   # публичный адрес (постоянный домен ngrok)
```

После загрузки весов интернет для обработки видео не нужен (туннель нужен только для публичного URL).
Подробнее: [README.md](../README.md).

## 2. Архитектура и модели

```
видео → детектор (геометрия сцены, люди) → VLM (состояния и проверки) → правила по таймлайну → ответ
```

1. **Сцена.** Детектор D-FINE-M (Objects365) находит стол кассира — тот, на котором стоит ноутбук.
   Координаты не зашиты, поэтому другой ракурс камеры не ломает разметку сцены (проверено на всех 42 видео
   и 16 чужих сценах MEVA).
2. **Скан.** Каждые 3–4 с VLM Qwen3-VL-8B смотрит на увеличенные фрагменты: рабочее место (есть ли кассир),
   каждого человека у стола (что в руках), при 2+ людях — сторону сотрудника (есть ли посторонний).
3. **Проверки.** Уход кассира: момент уточняется до ~0,75 с, затем отдельный вопрос по столу (деньги,
   инкассаторский мешок, документы) и по экрану ноутбука (рабочее приложение / экран блокировки).
   Телефон и еда засчитываются только при подтверждении на соседнем кадре. Кассир отличается от клиента
   по разметке рамок A/B на кадре.
4. **Ответ.** Описание собирается из наблюдаемых фактов по шаблону — свободный текст модели наружу не идёт.
   Норма подставляется из `rules/catalog.yaml`, только с `verified: true`.

| Компонент | Модель / средство | Лицензия |
|---|---|---|
| Детектор | D-FINE-M, Objects365 (`ustc-community/dfine-medium-obj365`) | Apache 2.0 |
| VLM | Qwen3-VL-8B-Instruct, GGUF Q4_K_M, через llama.cpp (`llama-server`, 4 слота) | Apache 2.0 |
| Сервис | FastAPI, очередь задач на диске, один GPU-воркер | MIT |

Железо: ноутбук с RTX 4060 Laptop 8 ГБ (модели занимают ~7 ГБ). Облачные AI-API не используются.
Лимит 300 с соблюдается гарантированно: у каждой задачи дедлайн от момента загрузки, при очереди время
делится между задачами, скан идёт «вразброс» по всему видео.

## 3. Перечень типов нарушений

Источник истины — [rules/catalog.yaml](../rules/catalog.yaml). Типы выделены по ручному просмотру
всех 42 обучающих видео ([video_review.md](video_review.md), [labels_types.csv](labels_types.csv)).

### Распознаёт сервис (8)

| id | Нарушение | Как проявляется на видео | Подтверждено на обучающих видео |
|---|---|---|---|
| `unattended_valuables` | Ценности оставлены без присмотра | деньги / инкассаторская сумка / кассовые документы на столе, кассира нет | да (Х-15, Х-24, Х-26) |
| `unlocked_workstation` | Компьютер не заблокирован при уходе | на экране рабочее приложение (не экран блокировки), кассира нет | да (Х-11, Х-28) |
| `food_drink` | Приём пищи / напитков | еда, чашка у лица кассира | да (Х-1, Х-46) |
| `personal_items` | Личные вещи на рабочем месте | сумка, одежда на столе кассира | да (Х-40) |
| `unauthorized_access` | Посторонний в кассовой зоне | второй человек на стороне кассира, передача предметов | да (Х-30) |
| `phone_use` | Мобильный телефон на рабочем месте | телефон в руке кассира | нет: Х-2, Х-20 найдены не всегда |
| `cash_count_without_client` | Пересчёт не в присутствии клиента | пересчёт начат после ухода клиента | нет |
| `cash_left_in_client_zone` | Деньги предыдущей операции на виду у следующего клиента | пачка на столе в момент входа нового клиента | нет |

### Размечены в обучающих данных, но сервисом не распознаются (3)

Эти типы описаны в каталоге и в разметке, но в ответе сервиса не появляются: видео с ними сервис
может пропустить.

| id | Нарушение | Как проявляется на видео |
|---|---|---|
| `door_left_open` | Дверь кассы оставлена открытой | после входа кассира дверь не закрыта |
| `cash_handling` | Пересчёт без счётчика / детектора подлинности | полистный пересчёт руками без оборудования |
| `collection_handover` | Нарушение приёма инкассаторской сумки | инкассатор оставляет сумку и уходит, не дождавшись проверки |

| `food_drink` | норма в актах РК не найдена | — |

**Принцип.** Пайплайн выдаёт `type_id`; текст нормы подставляется из каталога. Наружу попадают только
источники с `verified: true`. Каждая цитата в каталоге дословно сверена с текстом акта в базе «Әділет»
17.10.2026. Связь **прямая** — норма описывает само наблюдаемое поведение. Связь **косвенная** — норма
задаёт требование, из которого поведение следует (устройство помещения, настройка ИС, общая обязанность).
Если нормы нет, ссылку не выдумываем: тип выдаётся без источника.

В ответе API норма дописывается в конец `description`, а целиком (документ, пункт, цитата, ссылка) лежит
в дополнительном поле `rule` каждого нарушения — обязательные поля схемы ТЗ от этого не меняются.

### Качество (финальная версия v12)

Измерено `scripts/eval.py` на обучающем наборе (42 видео; разметка организаторов, типы — команды).
Отдельной отложенной выборки нет, поэтому на новых видео и другом ракурсе качество может быть ниже.
Модель отвечает не полностью детерминированно: между прогонами вердикт меняется на 1–2 видео.

| Показатель | Значение |
|---|---|
| Верный вердикт (accuracy) | 0,67 (28 из 42) |
| Найдено нарушений (recall) | 0,73 (16 из 22) |
| Точность (precision) | 0,67 |
| Тип назван верно | 9 из 16 найденных |
| Таймкод в пределах ±2 с | 44% найденных |
| Время на видео | 20–60 с |
| 5 длинных видео загружены одновременно | все готовы за 228 с (лимит 300 с) |
| 16 чужих сцен MEVA, Full HD (`scripts/run_folder.py`) | 0 падений |

Порог выбран в пользу полноты: по FAQ пропуск нарушения недопустим, а ложное срабатывание —
нежелательно.

## 5. Ограничения и известные ошибки

**Данные**
- Обучающий набор мал: 42 видео, из них 2 дубликата. На большинство типов приходится 1–3 примера.
- Все видео сняты в одной комнате с близких ракурсов. Устойчивость к другому углу проверена только
  косвенно: стол находится детектором без зашитых координат, на 16 чужих сценах MEVA сервис не падает.
  Собственных роликов с другого ракурса нет; план съёмки — [shooting_plan.md](shooting_plan.md).
- Три размеченных типа сервис не распознаёт (раздел 3).
- Организаторы разметили только факт нарушения и секунду. Типы размечены командой вручную,
  часть случаев неоднозначна (см. ниже).

**Известные ошибки таймкода**
- Уход кассира: в разметке момент отмечен непоследовательно. В Х-26 и Х-28 метка стоит на вставании из-за
  стола (наша ошибка 0,5 с), в Х-15 и Х-11 — на выходе из комнаты (ошибка 7–8 с). Сервис ставит таймкод на
  вставание и прикладывает два кадра: вставание и пустой стол.
- Х-4, Х-47, Х-13 (ошибка 18–31 с): ручной пересчёт (`cash_handling`) сервис не распознаёт, а деньги на
  стороне клиента при смене клиентов в этих видео не находит; вместо них отмечается другое событие того же видео.

**Неоднозначные случаи в разметке**
- Х-13@47: конкретное нарушение по видео не однозначно, размечено как `cash_handling` условно.
- Х-30: отмечен вход постороннего (13 с), но дверь открыта уже с ~5 с — возможно, это два нарушения.
- Х-22: по кадру трудно отличить обои рабочего стола от экрана блокировки.

**Ограничения распознавания**
- Мелкие предметы: на видео 464×848 телефон занимает 10–20 пикселей; модель путает его с банкнотами
  или банковской картой (ложные Х-5, Х-8, Х-19; пропуск Х-20).
- `unlocked_workstation`: включённый экран сам по себе не нарушение (в контрольных видео горит
  экран блокировки). Обои рабочего стола от экрана блокировки модель не отличает (Х-22).
- `door_left_open`: положение стеклянной двери модель не различает ни по одному кадру, ни по паре кадров.
- `phone_use`: по видео нельзя определить, есть ли у телефона камера (критерий нормы).
- `cash_count_without_client`, `cash_left_in_client_zone`: нарушение определяется последовательностью
  событий (клиент ушёл / вошёл), а не одним кадром. Ошибка в определении людей ведёт к пропуску.
- `unauthorized_access`: инкассатор, законно стоящий рядом с кассиром при приёме сумки, может дать
  ложное срабатывание (Х-16).
- Кассир, стоящий у стола (упаковка, путь к сейфу), иногда принимается за ушедшего (ложные Х-14, Х-25).
- Освещение: сцены с выключенным светом (Х-11, Х-12) — отдельный риск; качество на них отдельно не измерялось.

**Эксплуатация**
- Сервис работает на ноутбуке команды: при выключении ноутбука или запуске на нём других задач,
  занимающих видеопамять, обработка замедляется или останавливается. Публичный адрес — ngrok
  с постоянным доменом.

**Нормативная база**
- Для `food_drink` нормы в актах НБРК нет. Такие правила обычно задаются внутренними документами банка.
- Для пяти типов связь с нормой косвенная (см. таблицу выше); из них сервис распознаёт три —
  `phone_use`, `unlocked_workstation` и `unauthorized_access`.
